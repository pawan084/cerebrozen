# Audit C — Backend (FastAPI + SQLAlchemy async + Postgres)

Date: 2026-08-04. Scope: `backend/app/` (api/routes, services, models, schemas, agent, core),
`backend/tests/`, `backend/alembic/`. Every point was checked against the code; things the docs
warn about that are in fact already handled (`/chat?limit` clamping, `POST /sleep` upsert-by-date,
region-aware `crisis.reply_suffix`, `Idempotency-Key` on moods/journal, consent-gated insight
inputs, `FOR UPDATE SKIP LOCKED` nudge claiming, StoreKit chain pinning, Stripe webhook
`processed_webhooks` idempotency, `_escape_like` on journal search, single Alembic head) are **not**
listed as findings — a few appear below only where a sibling path is inconsistent with them.

## Authorization & authentication

1. [SEC] Oracle `thread_id` is caller-supplied and never checked for ownership — `thread_id = payload.thread_id or str(user.id)`, so posting another account's user id (a UUID that appears in every `SafetyEventOut.user_id`, `/admin/users` row and export) resumes *their* LangGraph checkpoint: the model is fed the victim's conversation state and streams a reply from it (backend/app/api/routes/oracle.py:158)
2. [SEC] `POST /oracle/confirm` resumes an arbitrary `thread_id` with the caller's own DB context — a guessed/known thread that is paused on `interrupt()` can be approved by anyone; the write tool then executes with `current_user_id` = the *attacker*, so the victim's proposed `save_journal(title, body)` arguments are committed into the attacker's journal (backend/app/api/routes/oracle.py:215, backend/app/agent/tools.py:143-148)
3. [SEC] `_record_decision` is correctly user-scoped but is the *only* scoped part of the confirm path — the audit row refuses to move while the graph itself resumes anyway, so the audit trail records "nothing happened" for a write that did (backend/app/api/routes/oracle.py:192-205 vs :215)
4. [SEC] `oracle_audit.open_pending` / `resolve` match on `thread_id + tool` with **no `user_id` predicate** — with client-chosen thread ids, one account can close another's pending audit row as approved/declined (backend/app/services/oracle_audit.py:69-75, :93-101)
5. [SEC] StoreKit receipts are verified but never bound to the caller — `verify_transaction` checks signature, chain and `bundleId`, and `tier_for` maps the product, but nothing compares `appAccountToken` to `user.id` and no `originalTransactionId` is stored, so one shared/leaked signed transaction can be POSTed by unlimited accounts for permanent premium (backend/app/api/routes/users.py:119-139, backend/app/services/appstore.py:158-172)
6. [SEC] The App Store webhook has no replay/idempotency guard while the Stripe one does — Apple retries on non-2xx, and a re-delivered `EXPIRED`/`REVOKE` after a re-subscribe downgrades a paying user; `ProcessedWebhook` exists and is used only by Stripe (backend/app/api/routes/webhooks.py:34-61 vs :90-98)
7. [SEC] Account enumeration on signup — `409 "Email already registered"` contradicts the deliberate non-enumerating design of `/auth/otp/request` and `/auth/password/forgot` in the same file (backend/app/api/routes/auth.py:64-66 vs :202-205, :320)
8. [SEC] Login leaks account existence twice more: an unknown email returns before any bcrypt work (a ~100 ms timing oracle) and a locked account gets a distinct `403` message that only real accounts can produce (backend/app/api/routes/auth.py:86-96)
9. [SEC] Password-reset tokens are replayable for their full hour — the token carries no `ver`/`jti` and `reset_password` bumps `token_version` without invalidating the link itself, so a leaked reset URL can be redeemed repeatedly (backend/app/core/security.py:66-67, backend/app/api/routes/auth.py:331-344)
10. [SEC] `/auth/verify/request`, `/auth/verify`, `/auth/password/reset` and `/auth/logout` carry no `@limiter.limit` while every neighbouring auth route does — `verify/request` is an authenticated email-send amplifier (backend/app/api/routes/auth.py:294-314, :331)
11. [SEC] Waitlist join distinguishes `already_joined` from `joined` on an unauthenticated endpoint — a public membership oracle, in a file whose sibling auth flows go out of their way to avoid exactly that (backend/app/api/routes/waitlist.py:32-37)
12. [SEC] `python-jose==3.3.0` is unmaintained and carries published advisories (algorithm confusion / JWE decompression DoS); it verifies both our own JWTs and third-party Apple/Google JWKS tokens (backend/requirements.txt:19)
13. [SEC] The JWT algorithm is env-overridable and both encode and decode read the same setting, so a misconfigured `ALGORITHM` silently weakens (or, for an asymmetric value, breaks) verification with no boot guard (backend/app/core/config.py:21, backend/app/core/security.py:51,85)
14. [SEC] Push tokens and Web Push endpoints travel as **query parameters** on DELETE, so they land in access logs, proxy logs and browser history (backend/app/api/routes/users.py:545-561, :605-620)
15. [SEC] `/events` is deliberately unauthenticated, but `anon_id` is fully client-chosen with no signature — funnel/retention aggregates in `/admin/metrics/funnel` can be inflated or poisoned at 60 req/min/IP with no way to tell real installs from synthetic ones (backend/app/api/routes/events.py:32-55)

## Input validation

16. [SEC] `ChatSend.text` has `min_length=1` and **no max** — an unbounded body goes straight into the LLM prompt (cost), the transcript context and a `Text` column; `TTSIn` next door is capped at 5000 (backend/app/schemas/content_data.py:48-49 vs backend/app/api/routes/voice.py:30)
17. [SEC] `OracleSend.text` is likewise uncapped and feeds a streaming agent run (backend/app/api/routes/oracle.py:46)
18. [DATA] `JournalCreate.body` is uncapped (`str = ""`) against a `Text` column, and `tags` is an unbounded `list[str]` of unbounded strings written into JSONB — a single POST can store an arbitrary blob under a user's account (backend/app/schemas/content_data.py:29-33)
19. [BUG] `UserUpdate` validates nothing: `language`/`companion`/`timezone` are unbounded strings against `String(120)/(60)/(60)` and `region` against `String(8)`, so an over-long value is a Postgres `DataError` → 500 instead of 422 (backend/app/schemas/user.py:56-64)
20. [DATA] `timezone` is never checked against the IANA database — every consumer swallows the failure (`except Exception: tz = UTC`), so a typo silently moves a user's wind-down nudge, digest time and pattern hour-buckets to UTC with nothing surfaced (backend/app/schemas/user.py:62, backend/app/services/nudges.py:105-108, backend/app/services/digest.py:79-83, backend/app/services/insights.py:145-150)
21. [DATA] `region` is not validated against `crisis._REGIONS` — an unknown code falls back to the international default with no signal, which is the one place a wrong value costs a user the correct hotline (backend/app/schemas/user.py:63, backend/app/services/crisis.py:62-63)
22. [BUG] `PushTokenUpdate.push_token: str` is uncapped against `String(512)` → 500 on a long token (backend/app/schemas/user.py:67-68); `DeviceTokenIn` next door does bound it correctly (:99)
23. [BUG] `WaitlistJoin.source` is an unbounded free string against `String(60)` on a public endpoint → 500 (backend/app/api/routes/waitlist.py:16-18)
24. [BUG] `ContentBase.subtitle`/`image_url`/`audio_url`/`video_url` and every field of `ContentUpdate` are uncapped against sized columns, so an over-long admin paste 500s instead of 422ing (backend/app/schemas/content_data.py:92-127)
25. [API] `ContentBase.kind` accepts any ≤40-char string with no enum — `sleep|breath|soundscape|meditation|program|wind_down` is a hard cross-client contract (rails filter on it), and a typo'd kind creates an item no client will ever render (backend/app/schemas/content_data.py:95, backend/app/seed.py:28-52)
26. [DATA] `SleepLogCreate.date` has no sanity bound — a client-clock bug or a hostile POST can write a night in 1970 or 2099; the unique `(user_id, date)` constraint accepts it and it then anchors `weekly_summary`, trends and the wind-down nudge (backend/app/schemas/content_data.py:173-180)
27. [DATA] `bedtime == wake_time` yields `duration_min == 0` (the property has no zero guard) and a 0-minute night is averaged into `avg_duration_min`, the sleep×mood pairing and `_short_sleep` as if it were data (backend/app/models/sleep.py:32-38)
28. [BUG] `hash_password` calls `bcrypt.hashpw` directly while `SignupRequest.password`/`ResetPasswordRequest.new_password` allow 128 chars — bcrypt 4.x **raises** `ValueError` above 72 bytes, so a long passphrase 500s on signup/reset (`verify_password` catches the same error, which is how this stayed invisible) (backend/app/core/security.py:19-27, backend/app/schemas/auth.py:6,45, backend/requirements.txt:20)
29. [DATA] `MoodCreate.mood` is free text with no taxonomy check, yet `_NEG_MOODS`, `trends.ease_score`, `nudges.schedule_contextual` and `agentic._fallback_plan` all key off exact lowercase labels — an unrecognised mood silently drops out of every derived signal (backend/app/schemas/content_data.py:9-14, backend/app/services/insights.py:142, backend/app/services/trends.py:45)
30. [BUG] `?platform=` on `GET /users/me/devices` has no pattern, and anything that isn't `"android"` is answered with the **APNs** enablement flag — `?platform=windows` reports iOS delivery status (backend/app/api/routes/users.py:491-513, contrast `DeviceTokenIn.platform`'s `^(ios|android)$`)
31. [BUG] `verify_email` and `reset_password` call `uuid.UUID(data["sub"])` unguarded, unlike `get_current_user`, which catches it — a token whose subject is not a UUID 500s instead of 400ing (backend/app/api/routes/auth.py:309,336 vs backend/app/core/deps.py:27-30)

## Pagination, unbounded queries, N+1

32. [PERF] `limit` is clamped with `min()` but never floored on `/moods`, `/journal` and `/sleep`, so `?limit=-1` reaches Postgres as a negative LIMIT and 500s; `/chat` gets this right with `max(1, min(...))` (backend/app/api/routes/moods.py:37, journal.py:65, sleep.py:31 vs chat.py:68)
33. [PERF] `GET /admin/users` clamps neither `limit` nor `offset` — `?limit=10000000` serialises the whole user table through `UserOut` (backend/app/api/routes/admin.py:84-97)
34. [PERF] `GET /admin/safety` has no limit at all and returns every safety event ever recorded, ordered but unpaginated — the one admin list that grows fastest (backend/app/api/routes/admin.py:417-426)
35. [PERF] `GET /admin/content` and `GET /admin/media` return every row unpaginated (backend/app/api/routes/admin.py:177-180, :327-330); `GET /admin/waitlist` likewise (backend/app/api/routes/waitlist.py:40-43)
36. [PERF] Six user-facing lists are unbounded: `/insights/digest/history`, `/nudges`, `/safety-plan/me/history`, `/goals`, `/habits`, `/users/me/memory` — each grows without limit and none takes a cursor (backend/app/api/routes/insights.py:58-70, :84-94, safety_plan.py:106-117, habits.py:50-59, :176-186, users.py:331-351)
37. [PERF] `GET /content` and `GET /media/catalog` return the entire published catalogue on every app launch with no `limit`, `since` or ETag — the media catalogue is fetched pre-sign-in by all clients (backend/app/api/routes/content.py:42-49, media.py:29-33)
38. [PERF] `GET /journal/tags` loads every entry's `tags` column for the user and de-duplicates in Python; this is `SELECT DISTINCT jsonb_array_elements_text(...)` work being paid for in application memory on every composer open (backend/app/api/routes/journal.py:70-91)
39. [PERF] `GET /admin/agent-actions` selects **all** `agent_actions` rows and aggregates in Python — a `GROUP BY tool, status` returns the same five numbers (backend/app/api/routes/admin.py:566-577)
40. [PERF] `recommendations.acceptance_stats` does the same full-table load, and nothing routes it — it exists only for a test (backend/app/services/recommendations.py:108-125, backend/tests/test_recommendations.py:151-159)

[PERF] `dispatch_due` is N+1 twice over: `db.get(User)` per due nudge, then `notifications.deliver` issues its own `device_tokens` query per user, then `webpush.send_web_push` another — one pass over 1000 due nudges is ~3000 round trips (backend/app/services/nudges.py:153-160, notifications.py:125-132, webpush.py:34-38)
42. [PERF] `digest.run_weekly_pass` loads every active user and runs the full `compute_weekly` (6+ queries each, incl. a 60-day mood scan) **on every dispatcher tick** — default `NUDGE_DISPATCH_INTERVAL_MINUTES=5`, so the cost is paid 288×/day to discover the same idempotent no-op (backend/app/services/digest.py:137-153, backend/app/main.py:41-49)
43. [PERF] `POST /admin/nudges` with no `user_id` inserts one row per active user in a single transaction with no cap, batching or dry-run (backend/app/api/routes/admin.py:494-519)
44. [PERF] `GET /users/me/export` materialises 13 tables into one JSON response with no streaming or pagination — a heavy chat user is an OOM-shaped response (backend/app/api/routes/users.py:199-235)
45. [PERF] `admin.user_detail` issues ~12 sequential round trips (6 counts + 4 `max(created_at)` + consent + contact) where two queries would do (backend/app/api/routes/admin.py:100-162)

## Indexes implied by query patterns

46. [PERF] Every hot user-scoped read is `WHERE user_id = ? ORDER BY created_at DESC LIMIT n`, but the models declare only a single-column `user_id` index — `mood_logs`, `journal_entries`, `chat_messages`, `insights`, `nudges` and `safety_events` all want a composite `(user_id, created_at DESC)` (backend/app/models/mood.py:14, journal.py:15, chat.py:14, backend/app/api/routes/moods.py:32-37, journal.py:48-66, chat.py:64-69)
47. [PERF] The free-tier quota counts `user_id + role='user' + created_at >= midnight` on every single message; without `(user_id, role, created_at)` this degrades linearly with a user's own history (backend/app/services/usage.py:32-41)
48. [PERF] `product_events` indexes `anon_id` and `name` but not `created_at`, while every funnel query is `name = ? AND created_at >= ?` with a `COUNT(DISTINCT anon_id)` — the analytics table is the one that grows fastest and scans widest (backend/app/models/product_event.py:21-26, backend/app/services/metrics.py:199-205)
49. [PERF] `dispatch_due` filters `status='scheduled' AND scheduled_for <= now` with `FOR UPDATE SKIP LOCKED` against two independent single-column indexes; a composite `(status, scheduled_for)` is what that claim query actually wants (backend/app/models/nudge.py:24-27, backend/app/services/nudges.py:144-151)
50. [PERF] `intervention_recommendations.open_recommendation` filters `user_id` + three `IS NULL` columns on every `/interventions/active` call (which the Home screen polls) with no partial index on the open state (backend/app/services/interventions.py:283-294)

## Races, idempotency, concurrency

51. [DATA] The idempotency record is written **after** the write commits, in a separate transaction — two concurrent retries of the same key both find no record, both insert a mood/journal row, and the loser's `IntegrityError` is swallowed; the duplicate the feature exists to prevent still lands (backend/app/api/routes/moods.py:53-67, backend/app/services/idempotency.py:100-115)
52. [BUG] Check-then-insert against a UNIQUE constraint, with no `ON CONFLICT` and no `IntegrityError` handling, in seven places — concurrent requests 500 instead of upserting: signup email, OTP `login_codes` row, waitlist email, `POST /sleep` (`uq_sleep_logs_user_date`), `POST /habits/{id}/complete` (`uq_habit_day`, i.e. an impatient double-tap), device-token register, web-push register (backend/app/api/routes/auth.py:64,208-214, waitlist.py:32-36, sleep.py:43-52, habits.py:249-256, users.py:531-540, :591-599)
53. [DATA] `snapshot_week` is "idempotent per ISO week" by a SELECT-then-INSERT with **no unique constraint on `(user_id, period)`** — the dispatcher runs in every gunicorn worker, so two workers ticking together write two Insight rows for the same week and `/insights/digest` returns whichever sorts first (backend/app/services/digest.py:44-73, backend/app/models/insight.py:14-22)
54. [BUG] `get_graph()` has no lock around its module globals — concurrent first requests build two graphs and two `AsyncConnectionPool`s (4 connections each), and the second `saver.setup()` races the first's `CREATE INDEX CONCURRENTLY` (backend/app/agent/graph.py:115-146)
55. [BUG] The checkpointer's psycopg pool is opened and never closed — the lifespan warms the graph but has no shutdown hook, so a reload leaks the pool (backend/app/agent/graph.py:88-96, backend/app/main.py:69-90)
56. [API] `POST /chat/messages` accepts no `Idempotency-Key` even though it is the most expensive write in the product; a retried send costs a duplicate user message, a duplicate LLM call and a duplicate safety scan (backend/app/api/routes/chat.py:73-137 vs moods.py:46, journal.py:99)
57. [BUG] `GET /plans/active` generates and commits a plan on a GET — two concurrent cold-start fetches both find no active plan, both call the LLM, and both insert (each deactivating the other's) (backend/app/api/routes/plans.py:23-34, backend/app/services/agentic.py:181-185)
58. [API] `GET /interventions/active` and `GET /recommendations/mine` also write and commit on a GET, which makes both non-idempotent and un-cacheable by any intermediary (backend/app/api/routes/interventions.py:42-49, recommendations.py:55-73)

## Timezone & date correctness

59. [DATA] "Today" is UTC everywhere the user experiences it as local: habit completion and `done_today` use `utcnow().date()`, so a habit ticked at 00:30 IST counts as *yesterday* and the seven day-dots shift for every user east of UTC (backend/app/api/routes/habits.py:149,248,270)
60. [DATA] `sleep.weekly_summary` and `interventions.gather_signals` window on `date.today()` — the *container's* local date, not `utcnow()` and not the user's zone; the rest of the codebase uses `utcnow()` (backend/app/services/sleep.py:26, interventions.py:229)
61. [DATA] `metrics.user_streak` groups by `func.date(created_at)` over `timestamptz`, i.e. UTC days, while the iOS/Android streak the contract says it mirrors counts *local* days — the two disagree by one day for any user whose evening check-in lands after UTC midnight (backend/app/services/metrics.py:55-65, docs/ARCHITECTURE.md:284)
62. [DATA] `compute_patterns` mixes zones inside one function: the hardest-time-of-day bucket converts to `user.timezone`, the weekday-rhythm rule three rules below uses raw UTC `created_at.weekday()` (backend/app/services/insights.py:172-174 vs :239)
63. [DATA] Two endpoints make the same sleep↔mood claim from **different pairings** — `compute_weekly` pairs a mood with the *same* UTC date's diary row, `trends.compute` pairs a night with the *next* day's check-ins; the same user can be told "mornings after 7+ hours read calmer" on one screen and shown `no_clear_link` on the other (backend/app/services/insights.py:122-131 vs trends.py:146-153)
64. [DATA] The weekly insight's own windows disagree: moods/journal use `now - 7 days` (a timestamp) while sleep uses `(now - 6 days).date()` — six nights against seven days in one summary (backend/app/services/insights.py:28 vs :77)
65. [DATA] `programs._view` computes the current day from a UTC date difference, so a user in IST rolls over to "day 3" at 05:30 local, and `days` is a client-supplied 1..60 that never has to match the program's actual `day_guides` length (backend/app/api/routes/programs.py:25,29-30)

## Safety pipeline & consent

66. [SEC] `voice_storage` and `model_training` consents are collected, stored, exported and shown in admin — and enforced at zero read/write sites (grep: the only non-schema references are the admin detail payload). Two of the six DPDP itemized categories are decoration (backend/app/models/consent.py:19-25, backend/app/api/routes/admin.py:155-156)
67. [SEC] Mood notes skip the safety pipeline — `MoodCreate.note` and `.trigger` are 255 chars of free text that go straight to the DB with no `scan_and_record`, while journal and chat both scan; "trigger: I want to die" produces no event, no resources and no escalation (backend/app/api/routes/moods.py:59-67 vs journal.py:111-118)
68. [SEC] The Oracle's `log_mood` tool writes an unscanned `note` for the same reason, on the one path where the model itself chose the text (backend/app/agent/tools.py:123)
69. [SEC] `POST /users/me/memory` (2000 chars of user prose the AI is told to remember) and `POST /goals` (`why`, 2000 chars) are unscanned write paths (backend/app/api/routes/users.py:354-371, habits.py:62-72)
70. [API] A journal POST that scores `crisis` returns only `risk_level: "crisis"` — no `resources` block, unlike `/chat` (region-aware suffix) and `/oracle` (a `crisis` SSE frame). Every client therefore hand-mirrors the hotline directory for this one path (backend/app/api/routes/journal.py:121 vs chat.py:127-129, oracle.py:93-94)
71. [DATA] Chat safety events store `source_id=None`, so the admin queue can name the risk but can never point at the message it came from (backend/app/api/routes/chat.py:82-83)
72. [PERF] The safety classifier runs a full LLM round trip *serially before* the reply's LLM round trip, doubling chat latency; they are independent and could run concurrently (backend/app/api/routes/chat.py:82 → :125)
73. [SEC] `DELETE /users/me` does not purge the LangGraph checkpoint tables that `DELETE /users/me/memory` explicitly does — a deleted account's conversation state survives in `checkpoints`/`checkpoint_blobs`/`checkpoint_writes` (backend/app/api/routes/users.py:238-259 vs :286-295)
74. [DATA] That same wipe matches `thread_id LIKE '%<user_id>%'`, but `thread_id` is client-chosen (finding 1) — a thread named anything else is missed by both the wipe and the delete (backend/app/api/routes/users.py:288-294)
75. [DATA] `/users/me/export` claims "a complete copy" but omits habits + completions, program enrollments, intervention recommendations, pattern recommendations, device tokens, trusted contact and safety events — several of which the user can see in-app (backend/app/api/routes/users.py:204-235)

## Quotas, rate limits, cost

76. [SEC] Three LLM-spending endpoints have neither the per-account quota nor an IP limit: `POST /assessment/topics`, `POST /plans/generate` and `POST /goals/{id}/decompose` (the last two generate a 900-token plan per call) (backend/app/api/routes/assessment.py:18-34, plans.py:37-45, habits.py:113-129)
77. [SEC] `POST /voice/tts` bills ElevenLabs per call, is capped only by a 60/min **IP** limit, and is available to free-tier accounts with no `enforce_quota` — the same cost class the chat quota exists to bound (backend/app/api/routes/voice.py:59-71, backend/app/services/usage.py:55-66)
78. [SEC] `/oracle/confirm` runs a full agent turn (LLM + tools) with no `enforce_quota`, so every paused confirmation is a free turn on top of the quota'd one (backend/app/api/routes/oracle.py:208-217 vs :157)
79. [SEC] `POST /voice/stt` reads the entire upload into memory *before* checking the 10 MB cap — a 1 GB POST is buffered first and rejected second; the admin media upload does it correctly with `read(MAX+1)` (backend/app/api/routes/voice.py:48-52 vs admin.py:400-407)
80. [PERF] `POST /admin/content/{id}/narrate` blocks a worker for up to 300 s synchronously; with the default `WEB_CONCURRENCY=1` one narration stalls the entire API (backend/app/api/routes/admin.py:220-247, backend/app/core/config.py:24)
81. [PERF] `ai.complete` sets no client timeout for either provider, so a hung LLM holds a request (and its DB session) for the SDK default; `voice.py` passes explicit timeouts everywhere (backend/app/services/ai.py:53-73 vs voice.py:33,63)
82. [PERF] bcrypt hashing runs on the event loop (no `to_thread`), so each signup/login blocks every other request on that worker for ~100 ms — 20 logins/min/IP × N IPs is a cheap throughput attack against a single-worker deployment (backend/app/core/security.py:19-25)
83. [PERF] `prompts.get()` opens a **new** `SessionLocal` per call with no caching, and it is called on every safety classification and every chat reply — two extra connections per message (backend/app/services/prompts.py:44-60, backend/app/services/safety.py:76)

## Error shapes & API consistency

84. [API] Four distinct error shapes are reachable from one client flow: `{"detail": "..."}` (HTTPException), `{"detail": {code, limit, used, resets_at}}` (quota 429), `{"detail": [{loc, msg, ...}]}` (422 validation), and `{"error": "..."}` with **200-adjacent** semantics from slowapi's 429 — the quota/IP-limit pair is documented, the other overlaps are not (backend/app/services/usage.py:69-81, backend/app/main.py:103)
85. [API] Both webhooks answer failures with HTTP 200 and `{"handled": false, "reason": ...}` — correct for provider retry semantics, but it means a monitoring system sees 100 % success while entitlements silently stop updating; nothing counts or alerts on `handled: false` (backend/app/api/routes/webhooks.py:39-54, :77-111)
86. [BUG] `stripe_billing.verify_webhook` does `float(timestamp)` outside the try — a non-numeric `t=` in the signature header is an uncaught `ValueError` → 500 instead of the `StripeError` → 200 the caller expects; `payload.decode()` has the same exposure (backend/app/services/stripe_billing.py:135-142)
87. [API] `GET /content?q=` interpolates the term straight into `ILIKE` with no wildcard escaping, so a search for "100%" matches the catalogue — the exact bug `journal._escape_like` was written to fix, unfixed one file over (backend/app/api/routes/content.py:46-47 vs journal.py:18-24)
88. [API] `GET /admin/users?q=` has the same unescaped `ILIKE` (backend/app/api/routes/admin.py:93-95)
89. [API] `PATCH /admin/users/{id}/active` takes the new state as a **query** parameter while every other mutation in the file takes a body, and the account disable/enable is never logged — unlike `/admin/safety/{id}/excerpt`, which logs the admin id (backend/app/api/routes/admin.py:165-173 vs :444-449)

## Sequence & placement (round trips, things that belong together)

93. [API] The streak is a separate `GET /users/me/streak` from `GET /users/me`, so every Home render costs two calls for one screen's header; the streak is three cheap unions and could ride on the profile (backend/app/api/routes/users.py:68-79)
94. [API] A cold Home needs five round trips — `/users/me`, `/users/me/streak`, `/plans/active`, `/programs/active`, `/interventions/active` (+`/moods`) — none of which can be batched; there is no composite read anywhere in the API (backend/app/api/router.py:30-52)
95. [PERF] The Pattern screen computes the same 60-day scan **twice**: `/insights/patterns` calls `compute_patterns`, then `/recommendations/mine` calls `seed_for`, which calls `compute_patterns` again — the recommendations belong in the patterns payload, whose `reason` field is literally the pattern statement (backend/app/api/routes/insights.py:73-81, backend/app/services/recommendations.py:55)
96. [API] The Insights screen needs four calls — `/insights/weekly`, `/insights/patterns`, `/recommendations/mine`, `/nudges` — three of which re-read the same mood/sleep windows (backend/app/api/routes/insights.py:17-94)
97. [API] `GET /sleep` and `GET /sleep/summary` are always fetched together by every client, and the summary is derived from the same rows the list just returned (backend/app/api/routes/sleep.py:18-67)
98. [API] `POST /moods` returns only the stored mood, though the write may have just changed the streak *and* queued a contextual nudge — so the client refetches `/users/me/streak` (and, for the nudge, `/nudges`) after every check-in (backend/app/api/routes/moods.py:59-68)
99. [API] Two independent recommendation engines ship side by side with different schemas, different persistence and different dismiss semantics (`/interventions` = one open offer, cooldown; `/recommendations` = permanent dismissal) — clients render both on the same screens and nothing reconciles them (backend/app/api/routes/interventions.py, recommendations.py, backend/app/services/interventions.py vs recommendations.py)
100. [API] Push registration is spread over three unrelated surfaces on one resource — `PUT /users/me/push-token` (legacy single column), `GET/POST/DELETE /users/me/devices` (the real one), `GET/POST/DELETE /users/me/push-subscriptions` (Web Push) — and `dispatch_due` has to branch on all three at delivery time (backend/app/api/routes/users.py:479-620, backend/app/services/nudges.py:158-182)
101. [API] `GET /admin/waitlist` is defined in `waitlist.py`, outside the admin router, so it is the one admin route not covered by the router-level `get_current_admin` dependency (it re-declares its own) and it is missing from the admin module a reader would look in (backend/app/api/routes/waitlist.py:40-43 vs admin.py:47)
102. [API] `/nudges` (a user-facing list) lives in `insights.py`, and `/goals` + `/habits` share a prefix-less router tagged `["goals"]` — the OpenAPI grouping doesn't match the URL structure for three route families (backend/app/api/routes/insights.py:84, habits.py:36)
103. [API] `POST /assessment/topics` is a pure, cacheable read expressed as a POST, requires auth (while `/assessment/structure` doesn't), and duplicates a preference the profile already holds (backend/app/api/routes/assessment.py:18-34)
104. [API] `GET /content` returns program items with no enrollment state, so the Programs page must fetch `/programs/active` and join client-side to know which card is the live one (backend/app/api/routes/content.py:29-49, programs.py:101-108)
